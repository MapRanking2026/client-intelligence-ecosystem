# No-show architecture review (before implementation)

Reviewed 2026-11-17 against the local source.

- Live Call: `live-call-step.tsx` renders the approved guide/deck, client-only presentation window, start/end controls and autosaved capture. `touch-state-service.ts` saves drafts transactionally and starts the follow-through deadline on call end. The monthly-touch page renders the transcript wait panel separately.
- Transcript: `transcript-watch-service.ts` reads the linked Calendar event and attached Docs, filters actual dialogue, and stores the large payload as an artifact. `meeting-transcript-service.ts` also resolves Meet/Drive artifacts. `transcript-wait-panel.tsx` preserves the secondary manual exception. Neither `advanceTouchProgress` nor the processing service universally enforces a transcript today; do not claim a stronger existing server gate.
- Follow-Through: existing page runs score confirmation, editable notes, approved tickets, trackers, recap and Finish. Notes, score and tracker generation read transcript artifacts. Notes also accept captured AM notes. `finishBlockers` validates approved deliverables. Processing files notes using the existing client-book writer, creates tickets and updates trackers, sends the approved recap via Intercom, then hands off to QC. Recorded remote IDs support retries; this is not an external exactly-once guarantee.
- QA: current QC uses `qc-handoff-service.ts`, a transactional touch/index creation, frozen `followThroughChecklist` evidence, reviewer notifications and a 17-point rubric. AI pre-read currently needs a transcript; human scoring does not. Legacy `qaReview` remains separately supported.
- Calendar: linked `calendarEventId`, `scheduledAt`, `googleMeeting` and client next-touch data are used by sync. Google Meet service owns token refresh and event reads. OAuth currently asks for Calendar read-only. No existing availability/rescheduling interface or event-update implementation was found. Rescheduling therefore requires an additive editor and Calendar write consent; it must fail before resetting local workflow if permission/update fails.
- Email: agenda generation composes factual HTML with saved `emailSignoff`; sending reuses `sendAgendaEmailViaIntercom`. Confirmation email has recipient resolution. Loom must reuse these helpers and require explicit approval. A persisted send claim must prevent concurrent/retried sends; ambiguous delivery must require reconciliation rather than blind retry.
- State: optional additive fields on `MonthlyTouchRecord`, tenant-scoped Firestore paths, monotonic `prep/review/live/follow/qa` progress. Reschedule is the deliberate backward transition and must archive attempt-specific state first. Preserve account intelligence and prior prep; clear only attempt progress after Calendar success. Loom stays in live until approved send succeeds, then uses existing follow/QA routing.
- Plan: add typed no-show resolution/history and Loom materials; explicit unselected chooser; update the exact Calendar event; keep standby date; generate the existing deck and derive editable script from its presenter notes; use labeled alternative evidence in existing generators and QC. Never write Loom content into a transcript artifact or mark a transcript found. Change only the transcript checklist row for Loom, leaving other requirements in force.

Known integration limits: Calendar write consent must be granted after adding its scope. Intercom acceptance establishes send acceptance, not client inbox delivery. Live Calendar/Intercom/ClickUp behavior needs credentialed acceptance testing.
