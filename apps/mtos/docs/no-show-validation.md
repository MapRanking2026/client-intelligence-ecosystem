# No-show implementation and validation

The pre-implementation dependency map is in `no-show-architecture-review.md`.

## Implemented behavior

- Live Call has an unselected two-choice No-Show panel. Cancel does not mutate a record. Selecting a resolution appends history once; subsequent generation and send actions remain explicit.
- Rescheduling reads the AM's Calendar availability for the next 30 days, offers available starts on the selected date, and requires confirmation. It rechecks availability on the server, patches the existing event ID, preserves event duration/attendees/conference, and avoids another patch when the event already has the requested start. It does not verify client availability.
- After Google succeeds, a Firestore batch resets progress to Preparation and synchronizes the touch and client scheduling fields, including the manual date override. The prior attempt and transcript artifact are archived under the same touch's `attempts` subcollection. Preparation and account data stay available. Standby lasts until 48 hours before the meeting; server approval/progress guards enforce it.
- Loom reuses the presentation generator with asynchronous delivery instructions and derives an editable speaking script from presenter notes. Declined sections are excluded from the stored Loom deck and its export. Loom share URLs receive syntax/host validation; MTOS does not claim to verify recording contents, public access, or that a reviewer watched it.
- Email reuses recipient resolution, saved signature composition, HTML sanitization and the existing Intercom sender. Generation never sends. Approve & Send saves the edited draft first. Intercom acceptance and conversation ID are recorded; inbox delivery is not asserted.
- Transactional no-show claims serialize mutations. Safe failures may retry; uncertain sends cannot send again. Read-only reconciliation searches the connected recipient's Intercom conversations for one matching outbound subject and recording URL. An interrupted claim expires after ten minutes, while unresolved send status remains protected. Unverifiable outcomes remain blocked for operator reconciliation.
- Existing Follow-Through uses labeled preparation, script, deck, recommendations, account data and sent email evidence. Loom materials are never stored as a transcript. Health review remains explicit and does not invent a new client NPS. Existing notes, tasks, tracker, recap and finish approvals stay in place. Filed ClickUp notes are prefixed with the no-show type, recording URL and email reference, using the existing Client's Book writer and naming conventions.
- Existing QC receives its normal handoff. Only the transcript checklist row becomes a Loom documentation row. The QA screen exposes supporting materials and the AI pre-read receives labeled alternative evidence; video judgments remain the human reviewer's responsibility. The normal transcript wait panel and its secondary manual exception remain available for normal meetings.
- Loom processing is serialized and reminder tasks store their IDs/status to prevent blind duplicate creation. Existing integration IDs remain the basis for task retries. External services without idempotency keys cannot provide a cross-system exactly-once guarantee; ambiguous outcomes require reconciliation.
- Rescheduled transcript polling rejects writes for a changed scheduled date, ignores pre-meeting historical Docs, and cannot restore an old artifact while the new meeting is still on standby.

## Automated checks

- `npm run check`: passed Next.js route type generation, TypeScript and full-project ESLint on the final implementation. Next.js type generation required access outside the Windows filesystem sandbox to canonicalize the workspace path.
- `npm run check:no-show`: real no-show orchestration with in-memory Firestore and stubbed Calendar, presentation, email and profile services. Checks normal transcript checklist behavior; URL and all-day timezone validation; selection history deduplication; failed Calendar update without reset; successful reset/archive; Loom generation without email delivery; explicit send and no duplicate retry; safe failure retry; uncertain delivery and read-only reconciliation; concurrent claim rejection.
- `npm run check:no-show-ui`: isolated Playwright harness with intercepted workflow endpoints. Checks both unselected choices, cancellation without a request, editable script/email, invalid URL gating, generation without send, explicit approval, Follow-Through navigation, availability checking, confirmation before rescheduling, Preparation navigation, persisted uncertain-send status, disabled resend and read-only reconciliation. No browser page errors were observed. This harness does not test production styling or authenticated app integration.
- Browser checks used installed Chrome via `PLAYWRIGHT_EXECUTABLE_PATH=C:/Program Files/Google/Chrome/Application/chrome.exe`. The sandbox blocked local browser network access; the isolated tests passed with that restriction lifted.
- Existing regression checks passed: touch progress, stages, live call, transcript watch, touch approval, Follow-Through checklist, finish, notes, score, trackers, tickets, QC record, rubric, submit, and integration permissions.
- Existing `check:follow-through-recap` reports 52 passed and one failed assertion: it expects the missing-signature error to contain `unsigned`, while the current helper emits different signature-related wording. Neither that check nor its recap/agenda contracts was changed by this enhancement.
